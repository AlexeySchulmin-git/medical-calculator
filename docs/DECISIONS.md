# Архитектурные решения Medical Calculator

## 🏗️ СТРУКТУРА ПРОЕКТА

### Почему выбрана такая структура папок

#### Двойная архитектура: Express + Next.js
**Принятое решение**: Два отдельных сервера
- **Express сервер** (`medical-api-server.cjs`) - основная бизнес-логика с PostgreSQL
- **Next.js приложение** - фронтенд и дополнительные API с MySQL

**Причины**:
1. **Легаси код**: Express сервер уже существовал с рабочей логикой расчётов
2. **Разделение ответственности**: Основная логика изолирована от фронтенда
3. **Разные БД**: PostgreSQL для заказов (надёжность), MySQL для клиентов (исторически)
4. **Независимое масштабирование**: Серверы можно разворачивать отдельно

#### Папка `src/` для исходников
**Принятое решение**: Весь исходный код в `src/`
**Причины**:
1. **Чистое разделение**: Сборочные файлы (`next.config.ts`, `package.json`) на верхнем уровне
2. **Логическая группировка**: `lib/`, `widget/`, `app/` по назначению
3. **Современный стандарт**: Соответствует best practices для Next.js

#### Виджет в `src/widget/`
**Принятое решение**: Отдельная папка для виджета
**Причины**:
1. **Независимая сборка**: `widget-build.js` собирает отдельный bundle
2. **Preact вместо React**: Меньший размер для встраивания
3. **Custom element**: `<medical-calculator>` для лёгкой интеграции

## 🚫 НЕСТАНДАРТНЫЕ РЕШЕНИЯ

### 1. Смешение CommonJS и ES Modules
**Решение**: Express сервер в CommonJS (`.cjs`), остальное в ES Modules
**Причины**:
1. **Совместимость**: `pg` и другие пакеты лучше работают с CommonJS
2. **Простота**: Не нужно настраивать `type: module` для всего проекта
3. **Изоляция**: Express сервер полностью независим

### 2. Две разные базы данных
**Решение**: PostgreSQL для заказов, MySQL для клиентов
**Причины**:
1. **Историческое**: MySQL уже использовалась для клиентов
2. **Надёжность**: PostgreSQL лучше подходит для финансовых данных (заказы)
3. **Миграция**: Постепенный переход на PostgreSQL без простоя

### 3. Preact для виджета
**Решение**: Preact вместо React в виджете
**Причины**:
1. **Размер**: Bundle на 40% меньше
2. **Совместимость**: API идентичен React
3. **Производительность**: Быстрее инициализируется

## 🔒 ЧТО НЕЛЬЗЯ МЕНЯТЬ И ПОЧЕМУ

### 1. Структуру `src/`
**Запрет**: Переименовывать или перемещать папки в `src/`
**Причина**: Сломаются все импорты и сборка виджета

### 2. Двойную архитектуру серверов
**Запрет**: Объединять Express и Next.js в один сервер
**Причина**:
- Риск потерять работающую логику расчётов
- Сложная миграция БД
- Потеря независимого масштабирования

### 3. Custom element виджета
**Запрет**: Заменять `<medical-calculator>` на React компонент
**Причина**: Потеря универсальности встраивания

### 4. Формат ценообразования
**Запрет**: Менять логику расчёта цен в `src/lib/calculator.js`
**Причина**: Сломаются все интеграции и существующие клиенты

### 5. API ключи в headers
**Запрет**: Переносить API ключи в query параметры
**Причина**: Безопасность и соответствие REST стандартам
